## 当前按键和回合语义

| 输入 | 当前新采集入口行为 |
| --- | --- |
| 315 | 开始新回合，默认15秒，包含十帧历史预热 |
| 308 | 成功结束，最后有效transition reward=1、terminated=true |
| 307 | 不成功提前结束，reward=0、truncated=true，原因manual_stop |
| 到时未成功 | reward=0、truncated=true，原因timeout |
| RB 311 | 按住配合摇杆人工移动，松开为零，不运行模型 |
| 304 / 305 | 当前入口忽略，不再需要人工保留/丢弃审核 |

307/308单独按即可，不需要RB；按RB不会屏蔽结束键。
不要同时按307与308：当前不同判定路径对冲突事件优先级不一致，仍待修正。
此前实现过人工保留/丢弃审核，底层仍保留，但用户最新要求是新入口强制review=auto。

状态：等待开始/人工复位 → 回合运行 → 成功/截断后零动作停止 → 后台完成保存 → 等待315。
后台保存完成不自动开始下一轮。回合外RB复位动作不进入训练样本；结束后要先松开再按RB，
避免仍按住的摇杆导致刚停止就继续移动。物理任务复位由人完成，无自动回位/拖动模式。
无有效观测、断连、回执缺失或写盘异常属于无效数据，不伪装成普通超时。

## 异步写盘与退出

原同步 `EpisodeSpool.append` 在控制线程压缩、写盘、fsync。
本机60条已有真实观测测速：每条原始数组约2.27MB、压缩约1.57MB，
耗时中位83.85ms、P95 88.85ms、最大90.06ms，占10Hz周期的大部分预算。

新入口使用 `AsyncEpisodeSpool`：主线程复制不可共享的数据快照，非阻塞提交32条有界队列，
独立线程顺序压缩/写盘/fsync。队列数组约73MB，加正在写的一条及元数据；不无限堆积内存。
回合中后台持续写，不是等结束才开始落盘；结束后补齐剩余写入及末条结果标签，再发布ready。
保存排空期间继续处理RB人工复位，但不启动下一段。
队列满或写盘错误中止该段有效采集，不允许静默丢帧后仍发布ready。

新实现按10Hz提交30条真实观测的短时测试：主线程提交中位0.96ms、P95 1.42ms、
最大1.58ms，队列最高积压1条，30条全保存，末尾排空约93ms。
这是本机短时结果，不保证长时、磁盘竞争或永久I/O阻塞下的延迟。测速临时文件已清理，原数据未变。

Ctrl+C优先请求停止，再完成正常收尾。完整回合保留；未完成回合已提交前缀用于审计，
不虚构成功或终止标签入池。重复Ctrl+C不打断正常收尾；断电/SIGKILL/永久磁盘卡死不保证完成。
退出后本入口不再提供手柄控制，软件停止不替代硬件急停。

异步改动仅接入新collect_rl_episodes入口；旧hil.actor、旧demo采集仍有各自同步存储路径。
目前没有历史帧去重；按早期压缩大小和连续10Hz有效采样粗估约56GB/小时，实际按内容变化。

## 已确认的按键缺陷（尚未修复）

`LinuxGamepad.poll()`读取一批事件后只保留每个键的最终状态，`ButtonEvents.poll()`再比较状态边沿。
若308或307的按下和松开出现在同一批，最终状态为松开，上层漏掉整次短按。
模拟原始Linux事件已复现：307/308短按均漏检，持续按住能检测，是否同时RB不改变结果。
只读检查实际 `/dev/input/js0`，按钮映射包含304/305/307/308/310/311/314/315/316/317/318，连接正常。
这证明存在代码缺陷，不证明用户每次漏识别的现场原因都已逐次追踪到。

当前日志不是按键即时确认：开始历史就绪后打印ACTIVE，保存结束后打印WAIT_RESET和结果。
需后续改为逐条消费事件、保留短按、统一307/308冲突规则并即时打印识别结果。
本轮仅排查，未修改LinuxGamepad或ButtonEvents以修复此缺陷。暂不将按钮测试结果当作真实奖励。
