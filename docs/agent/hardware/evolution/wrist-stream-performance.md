# 腕部视频流卡顿：排查、传输改善与ROI发布

更新：2026-10-03。本文是该问题的功能级纪传体；启动操作见[实时教程](../../../../tutorials/daimon_live.md)，
采集接口总览见[独立传感器采集](sensor-collection.md)。历史原始阶段结论保留在编年体，不因后续改善重写。

## 1. 当前结论

原默认实时入口已能采集，但用户观察到明显长停顿。相机完整JPEG接收/发布计数约30 Hz，
不绘图的ROS订阅却只有约10–12 Hz，曾超过1秒没有新图。可选大图共享内存组合配置后，
1080p原图在RViz并行运行的65秒测试中达到30.001 Hz、最长帧间隔72.48 ms。

因此，目前证据支持：**原ROS大图传输/接收配置是主要排查和有效改善方向**。
不是已证明相机SDK故障，也不能说已经找到了唯一底层根因。没有逐项消融共享内存容量、
传输选择和发布模式，不能断言只改某一个参数便足够，更不能断言原来完全没有使用共享内存。

当前另有full/roi启动开关；ROI为后续减少负载的功能，不是前述1080p改善的原因。
原默认入口未被替换，跨机器/Humble、长时间稳定性和曝光到屏幕时延尚未完成验收。

## 2. 先区分现象，避免把所有问题叫作延迟

| 现象 | 已有证据 / 边界 |
| --- | --- |
| 连续图像整体落后真实动作 | 需要曝光时间及同步或外部同拍验证；现有主机header不足以证明 |
| 突然停住，再跳到新画面 | 本机ROS订阅曾实测0.8–1.28秒新图间断；符合用户体验 |
| topic时间戳变化，但场景几乎不动 | 旧bag_004源图即近乎静止，不能仅凭hash/时间戳变化证明视频有效更新 |
| RViz窗口看不到 | 曾位于另一屏/隐藏，重开view后出图；与传输卡顿是两回事 |
| camera busy | 相机已有会话占用，用户关闭原会话后恢复，未抢占他人会话 |

新oct3_009旧录包检查中腕部确有场景运动，最大消息接收间隔约158 ms；触觉B deformation约650 ms。
这些录制事实不能由本机共享内存实验直接解释。其他机器未开RViz仍可能经过
ROS发布→rosbag订阅→写盘，但不因此认定它们与本机是同一个原因。

## 3. 数据路径与初始判断

本机当前路径：设备MJPG → UDP分片接收/重组 → 最新JPEG → 解码 → ROS Image → 订阅/RViz。
厂商参考预览通过SDK读图后OpenCV直接显示，绕过了ROS大图发布/订阅；
“厂商显示流畅”是有用线索，但不是两条完整链路已做同条件对照。

1920×1080三通道8位原图每帧6,220,800字节，30 Hz像素负载186.624 MB/s。
这是解码后的ROS图像负载，不是设备MJPG实测网络带宽，也不含协议、复制和其他传感器开销。
发布计数只说明代码调用了publish，不等于每个订阅者完整收到了该帧。

## 4. 实际排查步骤与结果

先保持采集/分辨率不变，只增加轻量、无绘图订阅诊断，记录源计数、订阅间隔与消息年龄。
随后才用独立配置重启腕部与显示端，触觉保持运行；未修改系统sysctl。

| 对照 | 接收率约 | 最长帧间隔 | 解释 |
| --- | ---: | ---: | --- |
| 初始同窗20秒测量 | 约12 Hz（233帧） | 1277 ms | 源计数约30 Hz，订阅端确有长断帧 |
| 普通订阅，队列1 | 11.59 Hz | 345 ms | 基线重复验证 |
| 订阅serialized bytes，跳过Python消息反序列化 | 12.23 Hz | 878 ms | 不是Python图像反序列化单独造成 |
| 接收队列30 | 10.33 Hz | 798 ms | 加大ROS消息队列未解决 |
| 再次队列1 | 11.76 Hz | 960 ms | 新进程一个UDP接收socket累计丢138个数据报 |
| 实际生效的大UDP缓冲，仅订阅端 | 9.15 Hz | 1105 ms | socket丢包计数0仍卡，缓冲不是全部解释 |
| 两端UDP配置＋同步发布 | 10.49 Hz | 640 ms | 仍未解决 |
| 大图SHM组合，初次15秒 | 30.01 Hz | 50 ms | 显著改善，未换SDK或降分辨率 |
| 项目实验入口，RViz并行，65秒 | 30.001 Hz（1949帧） | 72.48 ms | 无超过200 ms的间断 |

各行是顺序独立窗口，不是同一帧序列；只能作对照证据，不能用不同窗口计数推算精确丢帧率。
138是数据报数量，不是图像数量。额外诊断订阅也会带来负载，非零成本。

配置生效检查很关键：本机Fast DDS 2.14.6使用 `FASTRTPS_DEFAULT_PROFILES_FILE`；
仅设置较新命名变量时没有观察到预期缓冲变化。即使使用旧变量，旧 `ROS_LOCALHOST_ONLY`
设置下也未观察到预期效果；移除后，实际socket缓冲由212992增至8388608字节。
实验子进程改用 `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST`，不修改全局shell环境。
这记录的是本机验证结果，不保证所有ROS/DDS版本行为完全相同。

65秒窗口：帧间隔p95 45.02 ms；完整JPEG本机接收到订阅回调年龄中位22.11 ms、p95 26.23 ms、
最大62.33 ms。畸形帧/最新帧覆盖计数未增加，诊断socket未显示丢包。
这些不是RViz逐帧呈现测量，不含曝光、设备编码、此前网络传输和显示器刷新。

## 5. 发现但尚未证明是主因的问题

- 自写FCP1重组每片执行 `sum(map(len, chunks.values()))`，有重复遍历开销；
  只允许4个未完成帧、200 ms超时，厂商参考为64帧/500 ms。尚未以这些差异解释实际长停顿。
- 首版状态没有逐片丢失/重组过期完整统计，malformed=0不等于网络完全不丢包。
- 整体CPU短测仍有大量空闲、共享内存磁盘空间充足，不支持整机资源耗尽解释，
  但没有排除单线程、调度或DDS内部资源限制。
- 只看到streaming、低消息年龄或RViz渲染FPS都不能证明图像连续；必须同时检查帧间隔。
- SDK包装可减少协议维护工作，但如果仍保留有问题的ROS传输链路，不保证消除停顿。

## 6. 已落地方案及回退

- `scripts/start_daimon_shm_test.sh` 是独立实验入口，转交原launcher并选择 `--transport local-shm`。
- `ros2/omi_sensors/config/large_image_shm.xml`：64 MiB共享内存段、8 MiB单消息、loopback UDP辅助传输。
- 相机与RViz使用同步发布/本机发现组合；实际运行环境与共享内存文件大小已经检查。
- 原 `start_daimon_live.sh` 默认保持不变，停止实验camera/view后可用原命令回退。
- 同机优化，不作为远程显示方案；触觉采集/看板内部原环境契约未改，不宣称触觉已做同样优化。

## 7. ROI传输作为第二层减负

`--image-mode full|roi`，默认full；这是启动选择，不是热切换。

| 模式 | 发布话题 | 内容 |
| --- | --- | --- |
| full | `/omi/wrist/color/image_raw` | 原始解码BGR8图 |
| roi | `/omi/wrist/color/image_roi` | 既有(.500,.704,.36)裁剪，再nearest-rint-linspace至128×128 |

两者互斥发布，RViz/状态标签明确区分，文字不写入图像像素。1080p下裁剪边界为
x=766、y=566、宽高389，128输出每帧49152字节，理论像素负载约为整图的1/126.6。
与现有策略采样逐像素一致；旧人用看板Lanczos不变。策略下游仍需接入新topic、BGR转RGB、避免二次裁剪。
ROI真机8秒测量223帧、首尾间隔估计29.68 Hz，确认原图发布者0；GUI显示对应ROI标签和放大图。
相关测试52通过4跳过。ROI并不降低设备到本机的MJPG流量，尚未新增自动录包策略或CameraInfo。

## 8. 后续验证清单

1. 用户确认RViz实际观看的长停顿是否消失；做更长时间、实际运动的稳定性检查。
2. 测曝光到屏幕的端到端延迟，不以header年龄替代。
3. 需要远程显示时单独评估压缩/ROI与网络链路，不能照搬同机SHM。
4. 需要进一步追溯根因时，对SHM容量、传输选择、同步模式做单变量消融。
5. 旧bag直接解码视频与ROS回放分开比较；本次不替别人录制程序下结论。

临时诊断脚本 `/tmp/omi_wrist_receive_probe.py` 和截图可能被系统清理；正式启动器/配置在项目内。
该临时脚本尚未提升为仓库中的长期验收工具，这是复现资料的已知缺口。
