# 触觉分辨率、策略编码与采集吞吐

更新：2026-10-02。本文独立记录本轮讨论的当前状态，不是已实施的降采样方案。
形成过程见[编年记录](../chronicles/2026-10-02-tactile-resolution-and-throughput.md)。

## 当前倾向与实施边界

用户在比较完整场的30 Hz吞吐、存储成本后，最新倾向是：降采样到 **16×24** 也可以接受，
留待后续比较方案。它是候选尺寸，不是已经确定或已经上线的消息契约。
先前讨论的 **18×24** 来自现有箭头采样网格；两者不得混写。
当前采集仍保留SDK输出的空间尺寸，发布float32字段；本轮未改采集、网络、录包或旧看板代码。

看板主要用于流程检查和离线正确性检查；在线检查计划在另一台机器订阅topic运行RViz。
采集机仍承担序列化、网络发送开销，但不承担远端绘图。当前不以关闭/修改看板为优化重点。
SQLite3暂保留，没有当前负载下明显性能恶化的证据；MCAP只是待比较选项。
有界缓存只登记为现场观察项，当前不调整。

## 尺寸、类型与已验证数据

本文统一按高×宽×通道表示。直接读取本地
`local/tactile/record010_offline_fields_confirmed_v3/` 的A/B × 23、25.5、28秒六个NPZ：

| 内容 | 尺寸和类型 | 边界 |
| --- | --- | --- |
| 样本中的raw键 | 270×360 uint8 | 历史数据命名；不据此认定为新SDK的getRawImg输出 |
| 重建deformation、shear | 各288×384×2 float32 | 六组离线结果一致；不代表实机Flux直读已验收 |
| 重建/录制depth | 288×384 float32 | 与二维向量场不同 |
| 箭头渲染图 | 288×384×3 uint8 | 单场渲染、拼接缩放前 |
| 箭头采样网格 | 18×24个位置，每点两个分量 | step=16，offset=8；不是图片像素尺寸 |

现有renderer从完整场隔16点取样，最大432个箭头，deadband可能隐藏小箭头，过长箭头显示截断。
网络输入应保留采样后的有符号数值，不继承这些显示阈值/截断，更不能把红箭头当作已标定力。
ROS消息为 `sensor_msgs/Image`、`32FC2`，不是float16；`16UC1`是整数编码，不是半精度浮点。

## 候选数据路径与网络输入

| 方案 | 优点 | 代价或待验证点 |
| --- | --- | --- |
| 完整发送、完整录包，策略端降采样 | 可以反复比较分辨率，不额外丢失SDK已输出的场信息 | 带宽和磁盘成本高 |
| 采集端降至16×24或18×24，再发送/录包 | 大幅降低数值场载荷 | 丢失的细节不可恢复；需检验小接触/滑移 |
| 本地完整记录，远程发送稀疏预览 | 保留研究数据，降低远程查看带宽 | 不降低本地完整场录包成本 |
| 低分辨率传输，策略端再上采样 | 可适配某些预训练编码器 | 不恢复信息，也不节省放大后网络计算 |

16×24由288×384对应每18行、16列一个区域，18×24则对应16×16区域。
直接隔点取样可能漏掉局部接触；区域均值覆盖区域但可能抵消反向向量，方案尚未选定。
若重采样后仍沿用原SDK单位，向量幅值不能随图像尺寸任意缩放；应记录原始尺寸、
采样位置/区域、方法、单位及处理版本。16×24与原场长宽比不同，不应误认为原坐标等间距方格。
采样后接旧renderer需要适配坐标和步长，不能再次按step=16机械抽样。

每指deformation+shear共四通道，候选网络输入为 `4×16×24` 或 `4×18×24`（CHW），
先分别编码两指再融合；候选是小卷积、适配预训练骨干，不是画箭头图再识别。
视觉观测默认两路各128×128×3，裁剪方形ROI后缩放；旧触觉raw/depth观测默认64×64。
这是已有observation代码配置，不代表新SDK数值场已接入策略，或腕部采集已实现。

可以复用视觉/触觉的网络结构模板，但分别使用权重，允许入口通道、下采样次数不同，
统一最终特征接口，不必统一输入分辨率。用户明确提出利用已有预训练网络：
适配ResNet需要处理四通道入口、小尺寸过度下采样和触觉归一化，兼容层可加载预训练权重后微调；
自然图像预训练收益必须与同结构随机初始化对照，不能预先保证。
Sparsh是触觉图像预训练ViT，不是直接适配本项目四通道数值场的卷积权重。
上采样到128×128或保比例96×128均仅为讨论选项；上采样仍是四通道数值，不变成RGB。

## 30 Hz载荷估算与本机检查

以下是载荷算术，不是实机吞吐结果：假设两指各两个场、float32、30 Hz，相机640×480 RGB30。

| 数值场空间尺寸 | 四个场合计MB/s | 加相机后的MB/s |
| --- | ---: | ---: |
| 288×384 | 106.16832 | 133.81632 |
| 18×24 | 0.41472 | 28.06272 |
| 16×24 | 0.36864 | 28.01664 |

单位为十进制MB/s；未计触觉raw/infer、元数据、协议、文件索引及其他流。
16×24场载荷是完整场的1/288；这不是整套系统CPU或总带宽降低288倍。
完整场加相机约8.03 GB/分钟、481.74 GB/小时、1.07 Gbit/s；千兆链路无法承载上述完整未压缩载荷。
不能用旧合成源48×64的通过记录来证明完整尺寸30 Hz已经稳定。

本轮只读检查：Ultra 9 275HX、24核，约30 GiB内存/当时可用21 GiB；NVMe盘，
项目分区当时可用约120 GiB；`enp129s0`协商速率2500 Mbit/s。
这些是当时本机状态，不证明持续写盘吞吐、端到端网络或SDK性能，也不是其他部署机器的配置。
按完整场加相机估计，可用空间理论约16分钟，计入其他流与安全余量还会更短。

## 消息转换开销与证据限度

`tactile.snapshot`先复制SDK数组，再 `astype(np.float32)`；`node.image_message`再
`astype('<f4')` 和 `tobytes()`。两次astype默认复制，输入已为小端float32时存在重复复制。
保留快照的必要性不能因性能优化忽略；SDK内部更新与同frame ID校验仍需保证。
ROS消息构造、序列化、通信及消费者解码也有成本，不是上述NumPy测试的全部。

本机NumPy1.26.4合成微测试：每种方式9轮，每轮400次，取单次耗时中位数；保留初始复制、
两次有限性检查和bytes打包，仅将两处astype候选改为copy=False，不改项目实现。
64×64×2：约0.0049→0.0037 ms；288×384×2：约0.5305→0.5371 ms。
两路径bytes相等，但大尺寸没有显示明确加速。数字仅来自当轮终端测量，未形成独立基准脚本，
不含真实SDK/ROS/录包，不能宣称整机CPU下降；少复制的数据量也不是常驻内存节省量。

## 后续如何定案

1. 先用完整尺寸合成消息，再用真实设备验证30 Hz；统计帧号缺口、时间间隔、端到端积压、
   各进程/单核CPU、内存峰值、持续写盘与文件增长，不以topic非空代替无丢帧。
2. 留一批完整场作为对照，比较16×24、18×24及必要的更高分辨率，检查局部接触与时序滑移。
3. 对照网络编码效果、训练效果和资源量，决定正式发送/录制尺寸，而不是仅凭箭头看起来相同。
4. 若真实采集出现问题，再评估缓存与SQLite3/MCAP、无压缩/轻量无损压缩；当前不改。

以上是待实施的比较步骤，不是已经启动的测试或开发授权。
