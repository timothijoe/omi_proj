- `bash scripts/start_daimon_live.sh tactile`：独立双指采集组，既有实测约27–28 Hz。
- `bash scripts/start_daimon_live.sh camera`：腕部MJPG 1920×1080，设备协商30 FPS，状态streaming。
- `bash scripts/start_daimon_live.sh view`：订阅两组真实数据；GUI截图确认触觉与腕部图像显示。
- 相机状态计数5秒短测估计接收/发布约29.99 Hz；另一次8秒独立Image订阅100帧，首尾间隔估计12.53 Hz。
- 本机完整JPEG收到至发布抽样约11.59与14.78 ms；不是曝光到屏幕时延，也不是分位数统计。
- 短时状态曾显示malformed累计1、overwritten为0；未完整审计UDP分片丢失及所有帧号。
- 带3D的旧bag回放已关闭，关闭前保存当时视角/布局；实时采集保留。
- 实时RViz曾出现在另一屏且隐藏，恢复未正常生效后只重开view，截图确认在主屏出图；
  没有重启触觉或腕部采集。窗口可见性与当前视频卡顿是不同问题。

## 未解决问题与解释边界

1. 明显卡顿：源端采集、UDP、JPEG解码、ROS序列化/传输、订阅、绘图、RViz渲染及屏幕呈现
   各段尚未完成同窗测量，不能断言根因只在相机或DDS。
2. 约30 Hz与约12.5 Hz来自不同测量窗口，不能作为精确丢帧率。RViz显示的渲染FPS不等于新图像FPS。
3. 时钟未同步验证：图像header为本机完整JPEG接收时间，触觉为本机SDK取样时间；
   服务端时间仅原样保留，不用于计算已校准的单向时延。12–15 ms不能宣传为端到端延迟。
4. 触觉看板15 Hz、窗口布局尚粗糙；不存在“已达到低延迟统一看板”的结论。
5. 腕部内参发布、通用录包白名单与策略接入尚未实现；Humble真机未验证。
